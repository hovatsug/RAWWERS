# Deploy checklist

Every step a deploy needs beyond shipping the image, in the order they happen. Each item links to the entry in [BACKEND_GAPS.md](BACKEND_GAPS.md) that explains why it exists and what goes wrong without it - read that before skipping one. When a change adds a deploy step, it is added here in the same commit.

`[ ]` items are per deploy. Items marked **once** stay until the environment has had them done; tick them off per environment in the table at the end.

**The first deploy to the Hetzner server is run from [DEPLOY_RUNBOOK.md](DEPLOY_RUNBOOK.md)** (step by step, with what to see and how to undo each step); [DEPLOY_AUDIT.md](DEPLOY_AUDIT.md) (2026-11-21) lists what this checklist had wrong and what the code really does; [DEPLOY_SECRETS.md](DEPLOY_SECRETS.md) makes and rotates every secret.

## 0. Starting from an empty database (first production deploy)

Checked on 2026-11-17 against a throw-away Postgres and Redis with production-like settings (`APP_ENV=production`, dummy values), the API image and the code of that day. Each step's expected result is what that check showed.

1. **Settings.** The secrets file made from `deploy/.env.production.example` (`deploy/scripts/generate-secrets.sh` on the server). **Expected:** a wrong or missing one stops the API, workers and beat at start with every problem named (since 2026-11-21, `api/app/core/production_guard.py`: secrets empty, a development default or a placeholder; `AUTH_JWT_SECRET` under 32 bytes; a default database password; debug or bypass switches; console mail; a Stripe key that does not match `DEPLOYMENT_MODE`; `MUX_FAKE`; `API_DOCS_ENABLED`; CORS `*`, http or unset; non-https public URLs; empty `TRUSTED_PROXY_IPS`). Missing Mux keys do not stop it. Seen with every secret empty: 22 problems listed.
2. **`alembic upgrade head`** on the empty database. **Expected:** every migration runs, ending at the newest (`20261114_0098` on 2026-11-17); `alembic current` shows `(head)`.
3. **Start the API.** **Expected:** `GET /healthz` answers 200.
4. **Public reads.** **Expected:** `GET /v1/niches` lists the 12 niches (created on first use), `GET /v1/discover/pros` 200 with no photographers, `GET /v1/fx/rates` 200 with no rate until `fx-refresh` has run (section 3, M3), `GET /openapi.json` and `/docs` **404** (no API docs in production since 2026-11-21).
5. **The first admin.** Register the owner's account with `POST /v1/auth/register` (201, gives `user_id`), put that id in `ADMIN_USER_IDS`, restart the API, sign in (`POST /v1/auth/login`, 200). The admin role is added on the first signed-in request. **Expected:** with the `X-Admin-Api-Key` header, `GET /v1/admin/finance/currency-settings` 200 (the code's defaults: GBP only), `GET /v1/admin/shelf/settings` 200 (created on first read, the Shelf off), `GET /v1/admin/pros/review-queue`, `GET /v1/admin/bi/overview`, `GET /v1/admin/money-attention`, `GET /v1/admin/notifications/logs` all 200 and empty, `GET /v1/admin/pricing/niche-package-price-caps` 200 and empty.
6. **Reference data:** `deploy/scripts/dc run --rm api python scripts/bootstrap_reference_data.py` (2026-11-21; safe in production and twice; adds only what is missing, never changes a row). **Expected (rehearsal):** niches already there (12 skipped), GB tax rule 1, interview questions 5, camera models 98, lens models 13, price caps EUR 40 and GBP 40; a second run adds nothing. The pound caps are still the proposal of PRICE_CAPS.md: an admin changes them in the web admin.
7. **No feature flag rows are needed:** the defaults outside development keep the chat assistant off (section 2). **Expected:** `SELECT key, is_enabled FROM feature_flag` returns nothing on a fresh database.
8. **Run the exchange-rate job once** (`fx-refresh`, section 3, M3) instead of waiting for the beat's hourly run: `deploy/scripts/dc exec worker celery -A app.tasks.celery_app.celery_app call app.tasks.scheduled.fx_refresh` (the API and beat need outbound HTTPS to ecb.europa.eu). **Expected:** `GET /v1/fx/rates` then shows a GBP rate, so prices carry their approximations from the start.

Steps 2 to 5 (without the admin part of 5) run in CI on every change: the `empty-database` job of `.github/workflows/ci.yml`, with `scripts/check-empty-database.py` (its settings pass the production guards since 2026-11-21). Step 6 is one script now (`bootstrap_reference_data.py`).

## 1. Before deploying - checks against the target database

- [ ] **Paid gigs without a settled base payment.** Run the query in [DEPLOY CHECK: paid gigs without a settled base payment now release nothing](BACKEND_GAPS.md#deploy-check-paid-gigs-without-a-settled-base-payment-now-release-nothing). Any row is a client who chose photos and would be refused them. Fix the data before deploying; it is not a code change.
- [ ] **Reference data present.** Run the count query in [DEPLOY READINESS: production has no way to get the camera reference table or the price caps](BACKEND_GAPS.md#deploy-readiness-production-has-no-way-to-get-the-camera-reference-table-or-the-price-caps). Empty `camera_model_reference` sends every gear submission to review; empty `niche_package_price_cap` means the entry-price cap enforces nothing. The production bootstrap loads both (DEPLOY_RUNBOOK step 12, `scripts/bootstrap_reference_data.py`; the seed scripts refuse production by design). **The pound caps are PROVISIONAL** (owner not yet approved, [PRICE_CAPS.md](PRICE_CAPS.md)); the bootstrap says so on their line. Approved by the owner as PROVISIONAL for the test deploy only (2026-11-22). **Before launch: the owner reviews them with UK photographers** (PRICE_CAPS.md, "Before launch"), then approves them or corrects them in the admin (Settings > Price caps > choose GBP > edit or Import CSV…, Review, Save caps). To leave them out entirely, run the bootstrap with `--skip-price-caps`. Without the GBP caps, a photographer priced in pounds cannot create a package in any capped niche and tier.
- [ ] **Every active niche and tier has a price-cap row.** A missing (niche, tier) pair is not an error - `enforce_entry_price_cap` treats it as unrestricted - so a partial table looks configured while leaving whole niches uncapped. This must return no rows:

      SELECT n.slug, t.tier
      FROM niche n
      CROSS JOIN (VALUES ('rookie'), ('skilled'), ('pro'), ('elite'), ('master')) AS t(tier)
      WHERE n.is_active
        AND NOT EXISTS (
          SELECT 1 FROM niche_package_price_cap c WHERE c.niche_id = n.id AND c.tier = t.tier
        );

  A `master` row with no maximum is correct: master is uncapped by design, and the row has to exist anyway.

- [ ] **Duplicated reward-ledger references (migration `0079`).** `0079` adds a unique index on `reward_ledger_entry (user_id, entry_type, reference_type, reference_id)`. It first lists any existing duplicates and, if there are any, stops without changing or deleting anything. Run this first; it must return no rows:

      SELECT user_id, entry_type, reference_type, reference_id, count(*), sum(amount)
      FROM reward_ledger_entry
      WHERE reference_type IS NOT NULL AND reference_id IS NOT NULL
      GROUP BY 1, 2, 3, 4 HAVING count(*) > 1;

  Each row is an event credited more than once. Decide it with an admin adjustment, then deploy.

- [ ] **Run the integration tests against a live backend, and they must pass.** They cannot run against the test server (it is not this machine and has no `/v1/dev` routes), and the Mac no longer runs the dev stack day to day (2026-11-22). Run them against a throwaway API on this machine for the check only, then stop it: the e2e stack (`docker compose -f deploy/compose.e2e.yml up -d --build api`, `APP_ENV=test`, on port 8000; not yet tried for this) or the dev stack (`docker compose up` in `api/`). With the release candidate's `api/` up on this machine (a development or test `APP_ENV`), run in `app/`:

      flutter test --tags integration --run-skipped

  The summary must show **3 passed, 0 skipped, 0 failed**. An ordinary `flutter test` skips them by tag, and CI excludes them, so nothing else runs them: the real transport stack and the register-login-upgrade-logout flow are proven only here. Run on request they never skip. Before any test they check that the backend is on this machine and reports a development or test environment (`/v1/dev/environment`, which production does not have), and if it isn't, every test fails. The account the flow registers is deleted at the end of the run (`DELETE /v1/dev/test-accounts/me`), so a run leaves nothing behind.

- [ ] **Gigs made from requests that could not be booked.** Until confirm-slot checked the request it was answering, a photographer could make an unpaid gig from a request that had expired, that they had declined, or that the client had withdrawn. Count them:

      SELECT r.status AS request_status, g.status AS gig_status, count(*)
      FROM gig g
      JOIN booking_request r ON r.id::text = g.metadata->>'booking_request_id'
      WHERE r.status IN ('declined', 'cancelled', 'expired')
      GROUP BY r.status, g.status;

  Any row is a booking the client did not agree to, or no longer wanted. **Nothing deletes these automatically** - a paid one involves money and a person - so each is a decision: cancel and refund, or contact the client. Dev, 2026-10-12: none.

- [ ] **Admin tier overrides lost before migration `20261013_0059`.** Until then an override was undone by the first recompute after the hysteresis window - and rebuild-all, which this deploy runs, would have undone every one at once. `0059` keeps overrides (tier, admin, time, reason) and carries over any still in place; one already erased cannot be recovered from the skill row. List them from the event log, before and after migrating, and re-apply on the admin page (Photographers -> the photographer -> Niche tiers) any that should stand:

      SELECT e.pro_user_id, n.slug, e.to_tier, e.actor_user_id, e.created_at, e.reasons->>'note' AS reason,
             s.tier AS tier_now, s.override_tier
      FROM pro_niche_skill_event e
      JOIN niche n ON n.id = e.niche_id
      LEFT JOIN pro_niche_skill s ON s.pro_user_id = e.pro_user_id AND s.niche_id = e.niche_id
      WHERE e.event_type = 'admin_override'
        AND e.created_at = (SELECT max(created_at) FROM pro_niche_skill_event x
                            WHERE x.pro_user_id = e.pro_user_id AND x.niche_id = e.niche_id AND x.event_type = 'admin_override')
      ORDER BY e.created_at;

  A row where `override_tier` is empty after migrating is an override that was lost. Dev: none.

- [ ] **More than one refund in flight on one payment - before migration `20261018_0063`.** `0063` adds a partial unique index allowing one refund case in flight (`pending`, `requested`, `approved`, `refund_initiated`, `processing`) per payment intent. If two already share one, the migration stops and lists them rather than choosing; a refund record is money, so which one is real is a person's call. This must return no rows:

      SELECT stripe_payment_intent_id, count(*), string_agg(id::text || ' ' || status, ', ')
      FROM refund_case
      WHERE stripe_payment_intent_id IS NOT NULL
        AND status IN ('pending', 'requested', 'approved', 'refund_initiated', 'processing')
      GROUP BY stripe_payment_intent_id
      HAVING count(*) > 1;

  For each row, check the payment in the Stripe dashboard: keep the case that matches a refund Stripe has, and set the other to `cancelled` with a note in `admin_note`. Dev, 2026-10-18: none.

- [ ] **Paid payments left `pending` by an admin refund - repaired by migration `20261019_0064`.** Until then an admin refund marked its payment `pending` as soon as it was asked for, whatever the amount, so a part-refunded booking looked unpaid. `0064` puts each one back to `succeeded` (or `refunded` if its settled refunds add up to all of it) and records the amount refunded. Count them before migrating, so the change is known:

      SELECT count(*), sum(p.amount)
      FROM stripe_payment p
      WHERE p.status = 'pending' AND p.metadata ? 'paid_at'
        AND EXISTS (SELECT 1 FROM refund_case c
                    WHERE c.stripe_payment_intent_id = p.stripe_payment_intent_id
                       OR c.metadata->>'stripe_payment_id' = p.id::text);

  Dev, 2026-10-19: none. Each repaired booking's finals unlock again if the rest of it was paid - which is the point: a partial refund was never meant to lock them.

## 2. Deploying

- [ ] **The production image starts.** Build the `runtime` stage, which installs no dev dependencies, and import the app in it with the environment's settings (the server's secrets file is `/opt/rawwers/.env.production`, which `deploy/compose.prod.yml` reads through `deploy/scripts/dc`):

      deploy/scripts/build-and-push.sh <tag> <registry prefix> --no-push    # builds both images from the commit, checks them
      deploy/scripts/dc run --rm api python -c "import app.main; print('ok')"   # on the server, with its secrets file

  Expect `ok`. Without the settings the import stops at the first required one (`Field required`), and with unsafe ones the guard lists them, which says nothing about the image. Dev builds the `dev` stage (`BUILD_TARGET=dev`), which has every dev dependency too, so a production-only dependency that is missing never shows there: `httpx` was dev-only while the start-up warmup imported it, and the production image could not start. See [No dependency lockfile](BACKEND_GAPS.md#no-dependency-lockfile-pin-before-production---logged).
- [ ] **Client IP behind Cloudflare and Caddy (2026-11-11; Cloudflare 2026-11-21, `api/app/core/client_ip.py`).** The admin IP allowlist, every rate limit, download evidence and the risk signals key on the client's address. The chain is visitor -> Cloudflare -> Caddy -> API (admin calls: -> web -> API).
  - **Caddy is the only thing published** (`deploy/compose.prod.yml`; `api/tests/test_compose_prod.py` fails otherwise). Caddy trusts **no** proxy (`deploy/Caddyfile` has no `trusted_proxies`): it writes the address that connected to it, a Cloudflare edge, into `X-Forwarded-For`, replacing whatever the caller sent.
  - **`TRUSTED_PROXY_IPS`** = the compose network, pinned at `172.30.0.0/24` and set by the compose file; `TRUSTED_PROXY_HOPS=1`. Production refuses an empty value (every visitor would share Caddy's rate limit).
  - **`TRUST_CLOUDFLARE=true`**: `CF-Connecting-IP` is believed only when the hop that reached Caddy is in Cloudflare's published ranges, kept in one file (`api/app/core/cloudflare_ips.txt`, `CLOUDFLARE_IPS_FILE` to point elsewhere). From anywhere else it is ignored. Refresh monthly with `deploy/scripts/refresh-cloudflare-ips.sh`, then rebuild and update the Hetzner firewall. **Never** add Cloudflare's ranges to `TRUSTED_PROXY_IPS` or to Caddy's `trusted_proxies`, and never raise the hops to 2 for it (the earlier instruction): that trusts the caller's own `X-Forwarded-For` entries.
  - The Hetzner firewall admits 80 and 443 only from the same ranges (runbook step 2).
  - **Check after deploy:** `api/tests/test_client_ip.py` covers the spoofing cases. On the server, with `ADMIN_IP_ALLOWLIST` set to your address, an admin page opens from your address through `https://admin.rawwers.com`; from another network it answers "Admin endpoint not allowed from this IP". `/v1/admin/*` on the API host answers 404 (Caddy) whatever the headers.
- [ ] **Error reporting: Sentry, EU region (2026-11-11, `api/app/core/sentry.py`, `web/lib/sentry/`).** Off unless a DSN is set; nothing is sent from dev or tests.
  - In Sentry, create the organisation **in the EU region** (data in Frankfurt; DSNs end in `.de.sentry.io`), sign its DPA, and make two projects: `rawwers-api` (Python) and `rawwers-web` (Next.js). Done 2026-11-13: the `rawwers` organisation is in the EU region and both projects exist; their DSNs are kept outside git.
  - API, `worker`, `worker-photos` and `beat`: `SENTRY_DSN=<rawwers-api DSN>`, `SENTRY_ENVIRONMENT=production` (or `staging`), `SENTRY_RELEASE=<git sha>`. `SENTRY_TRACES_SAMPLE_RATE` stays `0` (errors only).
  - Web: `SENTRY_DSN=<rawwers-web DSN>` at run time, and `NEXT_PUBLIC_SENTRY_DSN` (the same DSN) as a **build argument** of `web/Dockerfile`, because the browser's copy is inlined at build time. No auth token is needed: no source maps are uploaded.
  - Web source maps (decide in the deploy plan): they are off (`sourcemaps: { disable: true }` in `web/next.config.mjs`), so admin-panel stack traces are minified; turning them on needs a Sentry auth token (`SENTRY_AUTH_TOKEN`) at build time, created by the owner and never committed.
  - What is sent: unhandled API errors and failed Celery tasks, ERROR log lines (an outbox event given up, for example), email failures that are not retried, admin-panel errors and the admin API's 5xx. Every event is scrubbed: no IP, cookie or email address, no authorization header, token, code or password (`scrub_event`, tests in `api/tests/test_sentry.py`). Each event carries the request id (`request_id` tag; for an unhandled API error since 2026-11-13, `api/tests/test_error_responses.py`), and every API 500 carries it in the `X-Request-Id` header and the body and the component (`api`, `worker`, `beat`, `web`).
  - **Check after deploy:** on the server, `docker compose exec api python -c "from app.core.sentry import init_sentry, capture_message; init_sentry('api'); capture_message('deploy check'); import sentry_sdk; sentry_sdk.flush()"`, then see "deploy check" in the `rawwers-api` project.
  - Set alert rules in Sentry: e-mail the owner on every new issue, and on `email_failure:config`.

- [ ] **`ADDRESS_ENCRYPTION_KEYS`** (new, required in production). Shipping addresses (The Shelf and prints) are encrypted on the server with these Fernet keys, comma-separated, newest first. The newest key encrypts; every key listed decrypts. Without it the API refuses to store an address in production. Losing every key makes stored addresses unreadable: keep it with the other secrets, backed up.
  - **Generate:** on the server `deploy/scripts/generate-secrets.sh` makes it (DEPLOY_RUNBOOK step 8); by hand, as [DEPLOY_SECRETS.md](DEPLOY_SECRETS.md) says, or `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` (44 characters, URL-safe base64). One key per environment; never reuse the dev or test server key in production. Dev and tests use a fixed key derived from a public string when the variable is unset; it protects nothing.
  - **Set it on every process that reads or writes addresses:** `api`, `worker`, `worker-photos` and `beat` read the same env file. A process without the new key cannot read addresses written with it.
  - **Rotate:** generate a new key and put it first, keeping the old one after it (`ADDRESS_ENCRYPTION_KEYS=<new>,<old>`); deploy all four processes. New and re-saved addresses use the new key; existing ones still decrypt with the old. The rotation table in [DEPLOY_SECRETS.md](DEPLOY_SECRETS.md) has the commands.
  - **Retiring the old key is not possible yet.** Nothing re-encrypts stored addresses with the new key (BACKEND_GAPS, The Shelf), so removing the old key from the list makes every address written with it unreadable. Keep old keys listed until that re-encrypt step exists.
  - **The postcode hash** (`shipping_address.postal_code_hash`) is keyed with the newest key, so it changes on rotation. Nothing matches on it today; anything that starts to must re-hash after a rotation.
  - **If a key leaks:** rotate as above at once; the leaked key can decrypt everything written with it until the re-encrypt step exists and has run.
